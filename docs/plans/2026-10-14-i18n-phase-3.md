# Starlight Ent. — Internationalization (i18n) plan, phase 3: language-aware stored text

> **For the implementer:** work through the tasks in order, on branch `claude/i18n-phase-3` (stacked on `claude/staff-contests-managers` @ `81f5e2b`, new PR). Each task ends with exactly one commit; do not merge tasks. After **every** task:
> - `tests/unit/p3-equiv.test.js` (task 1) is green **without** `-u`. It proves that the state, rendered back to Vietnamese, is byte-identical to the state the pre-phase-3 code produced. This is the "only the representation changed" proof.
> - The phase 1/2 Vietnamese display snapshots (`tests/unit/__snapshots__/ui-vi/**`, `ui-vi-extra/**`, `ui-vi-extra2/**`, `ui-vi.test.js.snap`, `toasts.json`) are green **without** `vitest -u`. The test *code* may wrap a helper result in `txVi()` before snapshotting (task 3), but snapshot files never change.
> - `tests/unit/i18n-state.test.js` is green: the same `JSON.stringify(S)` and the same `Math.random` call count for `vi` and `en`.
> - The e2e golden is either green unchanged, or regenerated **only** by the protocol in the "Golden master" section, and only in the tasks that section lists.
>
> If any of these goes red unexpectedly, stop, find the drift (usually a dictionary value that is not a verbatim copy, a param evaluated in a different order, an RNG call moved, or a reader that still prints a raw field), fix the code, then continue. Never run `-u` against the phase 2 snapshots or the phase 3 legacy snapshots.

**Goal:** Every piece of text the game **stores in `S`** becomes language-aware. A sink stores a key plus params (a *structured entry*), not a rendered Vietnamese sentence, and every screen renders it with `t()` at display time. Switching language then re-renders the whole history: the company log, artist history and lessons, busy titles, award categories, contest names, rival news, market modifiers, loan names, the weekly report's event list, GM problems, recruiter log, proposal reasons, health-check reasons, debut wishes, scandal texts, event reasons and the PR history. Saves made before phase 3 keep their Vietnamese strings as they are. Rendering accepts both legacy strings and structured entries.

**Done criteria:**
- With `lang=en`, a jsdom render of every surface **including the company log** (`#log`) contains no Vietnamese, apart from proper nouns: artist, manager, group and company names, and generated titles. The phase 2 rule that stripped long `S` strings before scanning is removed. Proven by `tests/unit/ui-en.test.js`.
- With `lang=vi`, every phase 1/2 display snapshot is byte-identical. New structured entries render exactly the bytes the old strings had.
- `p3-equiv.test.js`: rendering every structured entry of a fresh 56-week rich state (seed 7), a week-1 state (seed 42) and both e2e goldens back to Vietnamese gives JSON identical to what the pre-phase-3 code produced (recorded in task 1). Every number, id and order matches, so RNG order and gameplay are unchanged.
- Every `addLog`/`recLog`/`hist`/`lessons`/`busy`/`pushEv`/`prob`/`prHist` sink, plus the new sinks listed in task 1, contains no Vietnamese literal. The first argument of `addLog`/`recLog` is never a string or template literal (`tests/unit/i18n-sinks.test.js`, all files). At runtime, no stored text field of the rich state holds a Vietnamese string (`tests/unit/i18n-stored.test.js`).
- `node scripts/i18n-literals.mjs --strict` scans sink spans too (the exemption is removed). `scripts/i18n-literal-allow.json` shrinks from 123 entries to the `transfer.js` error messages (4) and at most the `FMT_VI` unit (see Open question 6).
- The data tables lose the Vietnamese display fields that only sinks used to read (`CONCEPTS[].n`, `OFFER[].n/lt`, `PLESSON[].n/lt`, `DRT`, `CFT`, ...), and the `tr = tVi` defaults are gone.
- Old saves (`tests/fixtures/save-v1.json`) load and show their legacy lines verbatim in both languages, and continue with structured entries. SL1 export and import round-trip structured entries.
- Save size: the compact and full saves of the rich state stay within **+10 %** of their pre-phase-3 size (recorded in task 1).

**Intentional gameplay change:** **No.** **Intentional change of `S` representation: yes.** Stored strings become structured entries, so the golden JSON changes (see "Golden master"). Values, ids, ordering and RNG call order do not change, and `p3-equiv` proves it on every task.

**Architecture:** This builds on phase 2 (`t`, `tVi`, locale parts, `labels.js`, the `sim.js` harness, the literal scanner). Phase 3 adds:
1. **`Txt`, the type of every stored text field:** `string` (legacy save or proper noun) `| Msg | tag`. `Msg = { k, p? }` is a dictionary key plus params. Params can themselves be `Txt` (nested messages and label refs such as `{k:'concept.cute'}`). Tags: `{$: n}` is money (units resolved at display time), `{$g: {stat: '1.3', …}}` is a stat-gain list, and `{$l: [Txt…], j}` is a list joined with the literal separator `j`.
2. **`src/i18n/index.js` additions (still a leaf):** `Lk(k, p)` builds a `Msg`. `tx(v)` renders a `Txt` in the current language and `txVi(v)` in Vietnamese. `isK(v, k)` compares a stored value with a key and accepts legacy strings through `tVi(k)`. `wkTok(w)` renders the log's `N{y}·T{w}` stamp. `t()`/`tVi()` now render `Txt` params recursively, so `t('ev.disband.d', {w: e.why})` works whether `e.why` is a legacy string or a `Msg`.
3. **Readers first, writers after.** Task 3 makes every display site and every logic comparison accept `Txt` while `S` still holds strings, so the golden stays green. Tasks 4–14 then convert sinks file by file, mechanically, with `Lk(...)`.
4. **Proof harness.** `p3-equiv` (legacy snapshots of state rendered to vi), the stored-text census, per-file sink rules, and a stored-key registry, because keys stored in saves are now a file format.

**Tech stack:** no new dependencies.

## Design decisions & rationale

1. **Representation: per-entry key + params (chosen), not a whole-string lookup.**
   - *Option A: keep storing Vietnamese, translate at display by reverse lookup (vi string → key, with regexes for the params).* No golden change and no `S` change, but about 400 regexes that are fragile with names containing punctuation, and ambiguous ("bạn thân" exists in two files). Phase 2 explicitly rejected reverse lookups.
   - *Option B: store `{k, p}` per text field (chosen).* The `Txt` union (`string | Msg | tag`) lets legacy strings coexist with no migration. A sink changes from `` addLog(`…${x}…`) `` to `addLog(Lk('log.area.name', {x}))`, a one-line mechanical edit. The cost is an intentional golden change, made provable by decision 5.
   - *Entry shape:* the log entry keeps `{t, c, w}`, and only `t` changes type. Flattening to `{k, p, c, w}` would save 5 characters per line but makes every stored field a special case. With one uniform rule ("a text field is a `Txt`"), the same `tx()` renders log, hist, lessons, busy titles and event reasons.
2. **Nested params are rendered inside `t()`/`tVi()` (chosen), not at each call site.** `fmtv(v, p)` first maps every `p` value that is a `Txt` object through the same language's renderer, then substitutes or calls the function value. Consequences:
   - Every existing `t('…', {w: e.why})` display site works with both representations, with no change: the event cards (`e.why`/`how`/`where`), `a.scandal.t` in `ev.scandal.d`, `s.concept` in `studio.sgl`, `a.evG` in `renew.lastEv`, `b.n` in `target.batch`.
   - Function-valued keys receive **strings**, so `'target.batch': p => \`thực tập sinh ${p.n.toLowerCase()}\`` keeps working when `b.n` is a `Msg`.
   - Strings, numbers, arrays and other objects pass through untouched, so no current call changes behaviour. The phase 2 snapshots prove it in task 2.
3. **Tags only where the text is language-dependent.** Money is the only formatting that differs (`fmt` units), so it is stored as `{$: n}` and rendered with `fmt(n, look('fmt.units'))`, which is byte-identical to `fmt(n)` in vi. `fmtN` (`K`/`M`), `toFixed`, percentages and ranks are language-neutral, so they are stored **pre-formatted** as strings or numbers. That keeps entries compact and avoids float re-formatting. Stat-gain lists (`"Vocal +1.3, Dance +0.8"`, from `applyLesson`, `projLesson` and `bonusTxt`) are stored as `{$g: {vocal: '1.3', dance: '0.8'}}` (strings keep the exact `toFixed(1)`/integer text) and rendered as `common.gain` (`'{s} +{v}'`) joined with `', '`. Generic lists use `{$l: [...], j: ' · '}` (proposal summary parts, secretary busy-title lists).
4. **Dual-use helpers return `Txt` (chosen), not `tr = Lk`.**
   - *Option A: keep the `tr` parameter and pass `Lk` from sinks.* This works for helpers that only nest `tr()` results (`debutRec`, `targetName`). It breaks silently for helpers that concatenate (`wkLabel`, `bonusTxt`), and it keeps a parameter whose wrong value only shows up at runtime.
   - *Option B (chosen): `targetName`, `bonusTxt`, `wkLabel`, `debutRec` (`why`, `short`) and `dOpts` return `Txt` built with `Lk`. UI callers write `esc(tx(helper(…)))`. The `tr` parameter and its `tVi` default are deleted.* `wkLabel` becomes one key (`common.wkLbl` = `'{w}{y}'`, with `y` an optional nested `common.wkYearSfx`). `bonusTxt` returns `{$g:…}`. A sink then stores the helper result directly. Until a sink's own task, a cross-file sink that interpolates a helper into a still-Vietnamese template wraps it in `txVi(…)` (a searchable temporary marker). Task 16 asserts `txVi` is used only in `src/i18n/` and in `review.js` `prHTML` (see task 10).
5. **Proof that only the representation changed: legacy vi-view snapshots, recorded before any change.** `tests/unit/p3.js` `viView(x)` deep-copies a state and replaces every `Txt` object with `txVi(v)`. Task 1 (unchanged `src`, where `viView` is the identity) records `toMatchFileSnapshot` files of `viView(richState(7,56))`, `viView(richState(42,0))`, `viView(tests/golden/week30.json)` and `viView(tests/golden/actions110.json)`. From then on, `viView` of the *new* states and of the *regenerated* goldens must equal those files. Equal money, fans, ids, `nid` and ordering mean the RNG stream is untouched, and equal text means the vi dictionary copies are verbatim. The test also runs `richState` under `en` and expects the same file, which proves language independence. This is stronger than the e2e golden: it runs in Vitest on every task, and it explains *where* a golden diff comes from.
6. **Logic on stored text: `isK` forward comparison (chosen), not migration.**
   - *Option A: migrate legacy enum strings to ids in `storage.js` (bump `S.v`).* This is the cleanest logic, but it is a reverse translation of old saves (against the confirmed decision), and it needs a version bump and fixture work.
   - *Option B (chosen): `isK(v, k) = v && typeof v === 'object' ? v.k === k : v === tVi(k)`.* New values compare by key and legacy values by their exact vi rendering. No migration, no version bump, and old saves behave identically. The cost is that the vi value of a key used in `isK` must never change. These keys are listed in the stored-key registry with a `logic: true` flag, and a fixture test pins their vi values (`tests/fixtures/legacy-enums.json`: `'Xuất sắc'`, `'Đang quay'`, `'tự duyệt'`, contest names…).
7. **Mechanical sink conversion with param order preserved.** Recipe below. The **param object lists values in the same order as the template's `${…}`**. Object literal properties evaluate left to right, so an inline RNG call inside a template (`market.js` raise log: `pick([...funds])`) keeps its position relative to the others. Never hoist a param into a `const` above other RNG calls.
8. **Keys are a save format, so they get a registry.** `tests/fixtures/stored-keys.json` lists every key (or `prefix.*` pattern for dynamic ones) that may be written into `S`. `tests/unit/i18n-stored-keys.test.js` asserts:
   - every `Lk('…')` literal and every `` Lk(`prefix${`` prefix in `src/` matches an entry;
   - every entry resolves in `vi` and `en`;
   - no stored value contains `<`;
   - `logic: true` entries match `legacy-enums.json`.

   The registry is **append-only**: removing or renaming an entry is a save-breaking change and needs a migration. The rule goes in the README.
9. **Locale parts for stored text:** `locales/{vi,en}/st-<area>.js`, one per writer task (`st-common`, `st-core`, `st-week`, `st-studio`, `st-lobby`, `st-mgr`, `st-meet`, `st-review`, `st-events`, `st-market`, `st-ext2`, `st-ext3`). ### Conversion recipe (tasks 4–14)

| Before | After | vi value (verbatim) |
|---|---|---|
| ``addLog(`💸 Lương ${a.name} tăng lên ${fmt(a.salary)}/tuần.`)`` | `addLog(Lk('log.ev.raise',{n:a.name,m:{$:a.salary}}))` | `'💸 Lương {n} tăng lên {m}/tuần.'` |

Rules:
- Copy the vi value **verbatim** from the template, including emoji, spaces, `«»`, `…`, `–` and trailing periods.
- Short param names (`n` name, `m` money, `t` title, `c` concept/category, `r` rank, `w` why/week, `x`/`g` optional suffix). The same name in the same key always has the same meaning.
- Keep params in template order (decision 7).
- Plurals and any value that needs code are function values in **both** locales (phase 1 rule).
- Never `esc()` a param in a sink: display escapes the whole rendered line, as before.
- Never mutate a stored `Msg`. Build a new one (`projLesson`'s live merge assigns a new `L.t`).

## Risks

- **A reader still prints a raw field** and shows `[object Object]`. Task 3 converts every reader first, using the checklist and a grep. Task 2 adds `expect(html).not.toContain('[object Object]')` to every surface render (vi and en) and to the extra cases. vi snapshots catch the rest within harness coverage, and task 1 adds extra cases for rarely reached stored texts (loan, mods, every disband/mmclash/intro/scout/scandal variant, PR history, film statuses, awards).
- **A dictionary copy differs by one byte** (an emoji variant selector, `–` vs `-`, a trailing space). `p3-equiv` names the field and the diff. Fix the dictionary, never the snapshot.
- **RNG drift** from converting a `pick` list, hoisting a param, or a new call to an RNG-using helper (`prPlans` from `prGo`, task 10). `p3-equiv` (numbers) and `i18n-state` (call count) catch it. `pickI` has its own seeded equivalence test (task 2).
- **Golden regeneration hiding a real change.** Regenerate only in the tasks listed, only after `p3-equiv` is green, and verify the regenerated goldens with `p3-equiv -t golden` before committing.
- **`isK` and legacy values.** A legacy comparison depends on the vi value of the key. `legacy-enums.json` pins them, and the registry flags them `logic: true`.
- **Key renames break saves.** Registry plus README rule (decision 8).
- **Shared objects.** `rep.ev` holds the same `Msg` objects as `S.log`, and `rep.a[].b` holds the busy title. JSON round trip duplicates them, which is harmless as long as nothing mutates a stored `Msg` (recipe rule).
- **Phase 2 tests that assert "S stays Vietnamese"** (`i18n-lobby`, `i18n-shared`, `ui-en-extra2` "data-t", `t10-prgo`) encoded the phase 2 contract. They are rewritten to the phase 3 contract in the task that changes the helper. The vi baselines they feed are unchanged.
- **Size.** Measured in tasks 1 and 16 (Open question 9).
- **Merge friction.** Tasks 4–14 touch disjoint sink sets, but `ext2.js`/`ext3.js`/`events.js` host shared helpers. Task 4 converts those helpers first. Work strictly in sequence.
